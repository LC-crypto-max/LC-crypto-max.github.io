AI 工具实践

从零使用-Code-X-Skill-构建-Spring-Boot-订单系统

一、写在前面

最近我尝试用 Codex 在命令行中从零构建一个 Spring Boot 后端项目。这个项目并不是为了单纯展示“AI 帮我写了多少代码”，而是想验证一个更实际的问题：

AI 编程工具能不能参与一个后端项目从需求拆解、代码生成、测试补充到代码审查的完整流程？

这次实践中，我选择构建一个简易订单系统，业务包括商品查询、用户下单、库存扣减、订单详情查询和订单搜索。技术上涉及 Spring Boot、MySQL、Redis、RabbitMQ、Elasticsearch 等常见后端组件。

整个过程中，我重点使用了两个 Skill：

  1. spring-boot-testing：用于补充 Spring Boot 测试；
  2. code-reviewer：用于对生成代码进行安全性、性能、结构和工程质量审查。

二、为什么要用 Codex？

传统使用 AI 的方式，更多是“在网页里问问题，然后复制代码到本地”。这种方式虽然方便，但上下文割裂比较明显。

而 Codex 更像一个本地开发 Agent，它可以在当前项目目录中：

  • 读取已有代码；
  • 创建新文件；
  • 修改代码；
  • 生成测试；
  • 更新 README；
  • 根据项目上下文持续迭代；
  • 结合 Skill 执行专项任务。

也就是说，它不是单纯回答问题，而是能直接参与项目构建。

我的理解是：

ChatGPT 更像一个问答助手，而 Codex 更像一个能在本地项目中工作的 AI 编程 Agent。

三、Skill 是什么？

普通 Prompt 是一次性的指令，例如：

而 Skill 更像一份可复用的专项工作流，里面包含某一类任务的规则、经验和执行标准。

比如：

  • spring-boot-testing 会告诉 AI：Spring Boot 项目应该如何选择测试方式；
  • code-reviewer 会告诉 AI：代码审查时应该关注安全、性能、异常处理、可维护性等问题。

所以 Skill 的价值在于：

让 AI 不只是“泛泛地写代码”，而是按照某个领域的最佳实践执行任务。

四、项目目标：构建一个简易订单系统

这次项目的目标是构建一个简易电商订单系统，主要包含以下功能：

  • 商品初始化；
  • 商品列表查询；
  • 用户下单；
  • 库存扣减；
  • 订单详情查询；
  • Redis 订单缓存；
  • RabbitMQ 订单创建事件；
  • Elasticsearch 订单搜索；
  • 测试补充；
  • 代码审查。

六、CodeX 的使用流程

这次我没有让 CodeX 一次性生成完整系统，而是采用了分阶段推进的方式。

阶段一：生成基础下单流程

第一阶段，我让 CodeX 先生成最基础的 Spring Boot 项目，包括：

  • pom.xml
  • application.yml
  • Controller
  • Service
  • Mapper
  • Entity
  • DTO
  • VO
  • 统一响应对象
  • 全局异常处理
  • SQL 初始化脚本
  • README 文档

这一阶段重点保证：

  • 项目结构清晰；
  • 基础接口能跑通；
  • 下单逻辑有事务；
  • 库存不足时能够抛出业务异常。

阶段二：接入 Redis、RabbitMQ、Elasticsearch

基础流程跑通后，再让 CodeX 逐步接入中间件：

  • Redis 用于缓存订单详情；
  • RabbitMQ 用于发送订单创建事件；
  • Elasticsearch 用于订单搜索；
  • Docker Compose 用于本地启动依赖服务。

阶段三：使用 spring-boot-testing Skill 补测试

项目生成后，我使用 spring-boot-testing Skill 来补充测试。

这个 Skill 的核心价值是帮助选择合适的测试方式：

  • Controller 层使用 MockMvc；
  • Service 层使用 JUnit + Mockito；
  • 复杂集成场景可以使用 SpringBootTest；
  • 测试顺序按照“主流程、边界场景、异常场景”组织。

阶段四：使用 code-reviewer Skill 做代码审查

测试补充后，我继续使用 code-reviewer Skill 对项目进行审查。

重点审查内容包括：

  • 下单事务是否正确；
  • 库存扣减是否存在超卖风险；
  • MQ 消息是否可能提前发送；
  • 消费者是否具备幂等处理；
  • Redis 缓存 key 是否合理；
  • ES 同步失败是否影响主流程；
  • Controller 是否写了过多业务逻辑；
  • README 是否完整；
  • 是否存在不必要提交的构建产物。

七、两个 Skill 分别起到了什么作用？

1. spring-boot-testing Skill：测试专家

spring-boot-testing 的作用是指导 Codex 生成更合理的 Spring Boot 测试。

它不是简单地让 AI “随便写几个测试”，而是会按照 Spring Boot 测试分层来选择方案。

比如：

它对我的帮助主要有三个：

第一，补充了测试思路。下单接口不仅要测成功，还要测库存不足、商品不存在、参数异常等场景。

第二，让测试代码更符合 Spring Boot 习惯。Controller 测试不一定要启动完整应用，而是可以使用更轻量的 Web 层测试。

第三，提高项目可信度。如果只是 AI 生成业务代码，可信度并不高；但如果同时补充测试，就更容易验证代码行为。

2. code-reviewer Skill：代码审查专家

code-reviewer 的作用是从工程质量角度审查 AI 生成代码。

它重点关注：

  • 安全性；
  • 性能；
  • 可维护性；
  • 异常处理；
  • 测试覆盖；
  • 代码结构；
  • 潜在 bug；
  • 配置问题。

在订单系统里，我重点让它检查：

  • 库存扣减是否会超卖；
  • MQ 消息是否在事务提交后发送；
  • Redis 缓存是否有一致性风险；
  • ES 同步失败是否影响主流程；
  • 消费者是否具备幂等处理；
  • 是否存在硬编码配置；
  • 是否有不应该提交的文件。

这个 Skill 的价值在于，它可以把 AI 生成代码中的潜在问题暴露出来，让我再进行人工判断和优化。

这次实践也暴露出一些 AI 生成项目中常见的问题。

1. 项目文件需要人工清理

但如果没有使用 @ConditionalOnProperty 控制 Bean 的创建，那么外部中间件没启动时，应用仍可能启动失败。

3. MQ 失败补偿需要继续完善

如果消费者同步 ES 失败，只是打印日志，那么消息可能已经被确认，后续不会自动重试。

生产环境中更合理的方案是：

  • 消费失败重试；
  • 死信队列；
  • 失败任务表；
  • 定时补偿；
  • ES 索引重建。

4. 订单号生成还比较基础

Demo 项目可能使用时间戳加随机数生成订单号。

真实分布式环境中，更推荐：

  • 雪花算法；
  • 数据库号段模式；
  • Redis 自增序列；
  • 日期前缀 + 分布式 ID。

5. 高并发下单还需要更多治理

但如果是高并发秒杀场景，还需要继续考虑：

  • Redis 预扣库存；
  • Lua 原子扣减；
  • MQ 异步落库；
  • 库存冻结与释放；
  • 订单超时取消；
  • 接口幂等 Token。

九、我对 AI 编程工具的理解

通过这次实践，我对 AI 编程工具的理解更加明确了：AI 更适合作为开发过程中的辅助工具，而不是完全替代开发者做技术决策。

在项目生成之后，我使用 code-reviewer Skill 结合 AI 对代码进行审查。它可以帮助我从事务控制、并发安全、缓存一致性、消息队列可靠性、异常处理和代码结构等角度快速发现潜在问题。相比人工从零开始检查，AI 能够提供一个比较系统的审查清单，帮助我提高代码复盘和问题发现的效率。

但 AI 给出的审查建议并不等于最终修改方案。比如它可能会建议增加 RabbitMQ 死信队列、接口幂等 Token、ES 同步失败补偿、Redis 降级策略等内容。这些建议是否需要立即实现，还是先写入后续优化计划，需要开发者根据项目阶段、业务复杂度和实际风险来判断。

所以我认为，AI 的作用是帮助我们更快地生成代码、更全面地发现问题，并提供优化方向；而开发者的作用是判断这些建议是否合理、是否必要，以及应该以什么优先级落地。换句话说，AI 可以辅助代码审查，但最终的工程取舍和风险控制，仍然需要人来完成。

十、后续优化方向

这个项目后续还可以继续完善：

  1. 增加 .gitignore，排除构建产物和本地依赖缓存；
  2. Redis、RabbitMQ、ES 组件改成 @ConditionalOnProperty 条件装配；
  3. RabbitMQ 增加重试队列和死信队列；
  4. ES 同步失败增加补偿任务；
  5. 订单号生成改为雪花算法；
  6. 下单接口增加 requestId 或 token 幂等；
  7. 增加订单超时取消和库存释放；
  8. 搜索接口增加分页、排序和时间范围过滤；
  9. README 增加架构图和面试讲解版本；
  10. 补充更多集成测试和异常测试。

十一、总结

这次实践最大的收获不是“AI 帮我写了一个订单系统”，而是我更清楚地理解了 AI 编程工具在真实开发流程中的位置。

它可以提高效率，但不能替代工程判断。

它可以生成代码，但不能自动保证系统可靠。

它可以辅助测试和审查，但最终仍需要开发者理解业务链路和技术风险。

我认为比较合理的使用方式是：

把重复性工作交给 AI，把关键风险判断留给自己。
